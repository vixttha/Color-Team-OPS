# Public information policy

Public materials use project branding and role-based attribution. Include only information necessary to understand, use, verify, or contribute to the software. Use the issue tracker for project contact. Preserve applicable license notices and required attribution.

Do not publish personal identifiers, private contact information, personal biographies, home or employer information, private social profiles, personal workstation paths, private account details, or credentials. Describe development arrangements only where necessary to reproduce technical results; use neutral role-based language. Preserve machine-readable protocol identifiers and genuine test evidence; do not misrepresent historical results.

Before publication, review documentation, source, all relevant refs, commit metadata, issue and review text, logs, artifacts, release assets, plugin packages and external sharing settings. Scan generated output before upload. Never put private matching terms into public source, workflow logs, job summaries or artifacts. Store any authorized exact-match terms outside the public repository. Use synthetic data in test fixtures. Report aggregate counts without personal values. Generic detection is not proof of anonymity.

Release acceptance requires a reviewed inventory, resolution of confirmed exposures, exact-revision evidence, and a separate human review of external surfaces. Historical edits require coordinated review because rewriting changes commit IDs and does not remove copies elsewhere. Use standard GitHub-hosted public runners for repository checks. Do not publish a release when required privacy checks are incomplete.
