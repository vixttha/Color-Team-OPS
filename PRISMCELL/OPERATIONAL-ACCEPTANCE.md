# PrismCell v0.0.1 — operational acceptance, explicitly scoped

**Decision:** READY FOR ON-DEMAND USE by nine named workcells. **NOT:** security-certified autonomous agents, independently authenticated specialists, always-on inboxes, product v0.0.2 acceptance, or owner approval to publish the plugin.

## Verified historical evidence and scope

- Nine specialist branches and nine canonical INCALL issues were installed without replacing legacy agent history.
- Final prior technical source: `50839b1c95e7390fbcd15366584e5592f7572d3e`. Previous native test evidence reported 48 Node and 15 Python/schema cases passed. This evidence remains historical at its exact SHA; no assertion is made that an installed agent/runtime was tested.
- Previous real GitHub message trials: 9/9 sender-recipient loops, constrained BLOCK decision, conflicting evidence review, stale-source rejection, checkpoint resume simulation, actual GitHub 409 compare-and-swap denial.
- Current v0.0.1 readiness activation adds **live** branch/issue/state checks and durable team startup checkpoints, not automatic model invocation.

## Required operational gate

Each team home must preserve old files, retain its source pin and release lock, reference its canonical issue, have no abandoned active worker, and explicitly record READY_ON_INVOCATION in STATE and OPERATIONS-CHECKPOINT. Handoff must direct next invoked worker to reread actual GitHub source, queues and incoming comments.

## Source and security boundary

Universal core, four JSON schemas and project config are separated. Configured team mapping checks are data validation, not an access-control decision. Actual GitHub `protected:false` flags and one connected admin actor do not prove independent least-privilege branch isolation. SHA-256 snapshots reveal edits only when trusted provider metadata is checked later; they are not authenticated signatures.

**Non-goals for this acceptance:** no new GitHub roles/rulesets, no paid service, no runner/CI dispatch, no installed plugin update, no automatic cross-team activation and no merge into integration/main. Any real always-on runtime requires a separately specified supported cloud processor, credential isolation and authorization tests.

## Release semantics

Finalization here means **workbench operational readiness**, not a software security certification or installed Color-Team-OPS release. The owner retains authority for broader publication and product release. Historical test claims must be revalidated after future code changes.
