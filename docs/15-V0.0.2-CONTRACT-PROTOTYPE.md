# 15 — v0.0.2 prototype state/evidence contracts (D1)

**Status: isolated future-v0.0.2 reference prototype, not installed or production-enforced.**

This milestone follows [the architecture decision register](13-V0.0.2-DECISION-RECORD-AND-ROADMAP.md) without touching v0.0.1, `main`, or Issue #4. Files are under `contracts/v0.0.2/` and do **not** replace legacy schemas. **No extra team or auditor conversation.** The 12-skill split remains nine specialist Workers plus Mission Control, OPS Director and Verification Gate.

## Data sequence

1. Head constructs `mission.schema.json` (mission state/authorization as claimed input, cloud_only=true, runner_required=false). Its `required_teams` and `allowed_teams` arrays must be cross-checked by a trusted policy implementation.
2. Head issues `work-order.schema.json`: one specialist task and criteria, exact source SHA, bounded repair, permitted action subset. Its `issued_by="HEAD"` is an **assertion**, never authenticated identity.
3. Worker produces `worker-event.schema.json` and `evidence-claim.schema.json`; it **cannot output PASS as a worker outcome** and cannot dispatch another team.
4. Verification Gate resolves evidence claim IDs against authenticated provider records, then creates a trusted-origin `gate-record.schema.json` for VALIDATE with PASS/FAIL/UNVERIFIED. A second, explicitly INTERNAL_AUDIT gate produces PASS/REPAIR/BLOCKED/UNVERIFIED. Neither is external independent human approval.
5. Head emits `head-decision.schema.json`, including references to both gate records for structural COMPLETE, but a real runtime **must re-fetch** gate statuses and bind them to the current source SHA and required acceptance criteria before accepting. A forged record ref remains a claim.
6. `transition-event.schema.json` lists the sequential cycle and actor labels. Head dispatches and closes; Worker→Validate→Internal Auditor→Head is the only affirmative completion path. Reusing the same Worker for an authorized repair still returns through the gated cycle.
7. Externally required release permission is tracked **separately**; `BLOCKED_EXTERNAL_APPROVAL` means internally valid work is not falsely presented as an authorized release.

## Structural versus trusted invariants
| Rule | Draft 2020-12 schema | Trusted host/runtime |
| --- | --- | --- |
| Known nine teams, action enums, 40-hex SHA | Yes | Must confirm actual branch/ref |
| Exact one-stage transitions | Yes | Must confirm live current phase and no replay |
| `COMPLETE` must carry validation/audit refs | Yes | Must authenticate both actual PASS records, current SHA and all criteria |
| One active worker | **No** | Head state machine; optional cloud lease for cross-session enforcement |
| Worker cannot choose next team | Worker message lacks authoritative dispatch | Only authenticated Head/gateway may authorize dispatch |
| Required team set is a subset of allowed team set | **No** | Policy validator required |
| Real provider evidence and authorization | **No** | Authenticated provider tool lookup, provider record matching |
| Global exclusive writer | **No** | Optional cloud lease + fencing + enforced write gateway; direct writer bypass limitation |
| Tests actually executed | **No** | Real job/step/fixture evidence |
| No personal runner dependency | `cloud_only=true`, `runner_required=false` | Product packaging/runtime audits |

## Schema changes vs v0.0.1
Legacy `mission.schema.json` uses `max_retries` and states `DRAFT/AUTHORIZED/...`, while the new prototype additionally separates workflow phase from mission state and adds `max_local_repairs`, `required_teams` and `mode`. Legacy completion uses `status` and `evidence_state`; prototype worker events use `outcome` and untrusted claim IDs, with **separate gate records**. Legacy routing includes `action`, `next_team` and optional `verification`; prototype Head decisions never trust worker PASS and reference distinct gate records. A migration must preserve legacy identifiers, semantics, audit history and deterministic rejection of unknown/lossy conversions; **no transparent silent upgrade or blanket backward-compatibility claim**.

## Gaps still blocking real v0.0.2 completion
- Authenticated principal, authorization reference and provider evidence resolvers are not implemented.
- No durable mission state, global lock, role-enforcing handler or cloud write gateway.
- These schemas cannot alone reject all forged or replayed events; content is untrusted until the host resolves it.
- Nine specialist behavioral quality suites and real ChatGPT trials remain NOT RUN.
- No owner-approved numerical thresholds, cloud provider, cost ceiling or plugin release decision.

## Proposed next engineering task
Implement a **pure local-free, host-agnostic policy reference verifier** that takes already-authenticated observations as explicit trusted inputs, checks cross-record invariants, and returns accurate UNVERIFIED/BLOCKED instead of inventing PASS. Build negative tests for stale SHA, replay, spoofed gate refs, role mismatch, external release gate and unavailable tools. Keep runtime cloud-only and never require personal runners.

## Fail-closed emergency-stop exception
The **successful** route still requires Head → Worker → Validate → Internal Auditor → Head. A Head-confirmed emergency **BLOCKED / CAPABILITY_BLOCKED / UNVERIFIED** transition may originate from HEAD_READY, WORKER_ACTIVE, VALIDATION_PENDING or INTERNAL_AUDIT_PENDING; that is **not successful completion** and requires immediate cessation of mutations. A Worker may report a hazard and stop acting, but cannot promote its own request to authoritative terminal state. Safety halts must never allow a direct COMPLETE transition. See `test_safety_halt_from_any_active_stage_by_head` and `test_worker_never_skips_directly_to_completion`.

## Important proof boundary tested
A structurally valid COMPLETE decision can contain **fabricated gate references**, which the JSON Schema cannot authenticate. The explicit negative-control test `test_a_valid_gate_reference_is_not_proven_provider_evidence` accepts the shape and documents why real provider-backed runtime verification is mandatory before mission acceptance.
