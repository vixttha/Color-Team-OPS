**Original tested Yellow reference:** `9b3ca3349016749ed4b809932b5a9e930ec3368b` ([260/260 dual-platform tests and read-only GitHub observation](https://github.com/vixttha/Color-Team-OPS/actions/runs/41016921417)).
**Status:** source change candidate / exact-new-SHA CI required. **NOT a production hosted identity implementation or live user-authorized mission.**

## Work performed in this change
A source audit found the reference `CloudAuthorityEngine` disallowed a specialist team after its first audited task, even when the owner consented to multiple separate handoffs. An ordinary bounded `Yellow → Orange → Yellow` repair sequence could not complete under the former `TEAM_ALREADY_COMPLETE` guard. The consent parser also constrained `max_handoffs` to fewer than the number of distinct teams, preventing a legitimate repeated-specialist journey.

The candidate patch:
1. Allows a previously audited team to be dispatched again for a **different task ID** only by Head, at the correct state, with the same exact-source checks.
2. Decouples explicitly consented `max_handoffs` from the count of distinct allowed teams while setting a **finite upper bound of 32**. Zero is valid, so simple missions remain one-team only by default.
3. Keeps `used_task_ids` and `used_receipts` replay protections, sequential Validate/Internal Audit, Head-owned completion, revocation, source checks and CAS.
4. Keeps `approved_teams` as a *deduplicated set-like audit summary*: completing Yellow twice does not manufacture a third specialist identity.
5. Adds three negative/positive tests: Yellow→Orange→Yellow completion, budget exhaustion preventing third dispatch, and refusal of more than 32 handoffs alongside same-team second-task approval.

## Genuine production-host acceptance — still blocked

No real protected cloud issuer, actual ChatGPT/OIDC exact-intent user consent, per-operation principal proof, managed multi-tenant transactional journal, protected immutable audit anchor, hosted revocation ledger, KMS, credential rotation, or real user-approved end-to-end hosted mission has been deployed.

Required independent **external-host integration evidence** before asserting production-authenticated completion:
- Owner selects and explicitly authorizes a replaceable supported cloud host, actual target tenancy and cost ceiling (no vendor may be made a product-wide prerequisite).
- Host issues purpose-scoped user grant bound to exact consent digest, repo identity, branch, revision, actions, teams, criteria, expiry and handoff budget **after actual human/host authentication**.
- Protected storage proves tenant isolation, atomic CAS in multi-replica concurrency, durable revocation/replay prevention across restart/failover/restore, independently retained audit chronology and no network-accessible dev SQLite.

- No broad write/exclusive mission authorization until a separately approved gateway/fencing implementation provides actual enforced protection and checks source permissions at mutation time.
- A separately scoped evaluator must distinguish role labels generated by one model from truly host-authenticated role principals; ordinary logical internal auditing is not an external independent human review.

## Known tradeoff and risk
Allowing repeated teams increases routing flexibility and also increases the possible number of tasks. The explicit consent digest includes the handoff budget; the finite 32 limit prevents unlimited dispatch through this contract, but a mission with the maximum budget may still incur costs. Future Head policy must separately cap actual API spend, repeated identical results and time; this limit alone is not an end-to-end economic budget.
