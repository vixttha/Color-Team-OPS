# CTO-V002 R-01–R-05 — portable coordinator contract migration and acceptance

**Scope:** existing mission `CTO-V002-SINGLE-THREAD`, source `integration/v0.0.2-master-single-thread`, master [#8](https://github.com/vixttha/Color-Team-OPS/issues/8), remediation [#19](https://github.com/vixttha/Color-Team-OPS/issues/19). Development-only implementation and review, **not a production/authenticated agent runtime**.

## Compatibility and contract version

- **Mission `schemas/mission.schema.json` (R-02):** existing required fields, state enum, `AUTHORIZED` and `authorization_ref` remain structurally supported. They are **declared metadata, not host permission**; optional `authority_claim_classification: DECLARED_ONLY` clarifies the boundary. Previous mission/example documents continue to parse, but **must not be used as proof of a real external grant**. Actual host capabilities, owner action scope, revocation, branch, task, current SHA and budget are checked per action.
- **Routing `schemas/routing-decision.schema.json` (R-01):** new `SUGGEST_ONLY` supports non-dispatch recommendations. Existing `BLOCK/IDLE/COMPLETE/ESCALATE/CAPABILITY_BLOCKED` objects retain their shapes. **Legacy bare `DISPATCH` is intentionally rejected** as unsafe: migrate a mere suggested specialist to `SUGGEST_ONLY` with `next_team`. A **Head-declared logical assignment** must include `next_team,task_id,source_sha,head_decision_ref,assignment_stage,authorization_ref,authority_claim_status=UNVERIFIED_HOST_AUTHORITY,authorization_effect=LOGICAL_ONLY_NO_HOST_GRANT,execution_authorized=false,active_worker_count=0,remaining_handoffs,evidence_refs`. The `INITIAL` stage requires no prior audit; `AFTER_REVIEW` additionally requires `prior_validation_ref,prior_audit_ref,verification=PASS` and its claimed source/time fields. Schema PASS/references can be self-authored: **neither schema nor JSON authorizes an external action**.
- **Completion event `schemas/completion-event.schema.json` (R-03):** legacy Worker event fields and examples remain valid. A new *optional*, versioned `workflow` object `schema_version=cto-v002-logical-chain-1` embeds task, stage, declared actor, unique predecessor, review disposition, bounded repair index, claim provenance and `authority_effect=NO_EXTERNAL_PERMISSION`. Alongside existing `event_id,mission_id,team,source_sha,evidence_refs,evidence_state`, each event is traceable. Full order and cross-event consistency require a sequence checker, not JSON Schema alone.
- **Development-only reference `policy_v002/coordinator_trace.py`:** `validate_logical_chain` checks the *represented* five-phase Head → Worker → Validate → logical Internal Auditor → Head order and initial/next/repair cases. It rejects duplicate/replayed IDs, missing or reordered stages, cross-mission/task evidence, stale SHA, overlapping Worker, forged roles, wrong retry/hand-off bounds. A successful result is `LOGICAL_VALID_UNVERIFIED`, **never** authenticated host PASS. `assess_external_action` demonstrates a per-action authorization check with synthetic `HostObservation`; these test objects are not actual provider identity or permission receipts.
- **Registry/router (R-04):** 18 IDs and the existing `requires_tools` fields remain unchanged and still denote prerequisites for **live actions/observed claims**. The development-only directory/router accept `advisory_only=True` and a nonempty supplied-context reference; they return `ADVISORY_ONLY` / `SUGGEST_ONLY`, never real tool grants. Red advice is synthetic-only without a real approved target. All nine existing specialist competency references and the embedded OPS Director table explain the same fallback. No new coordinator, specialist, vendor-specific runtime or packaged Python requirement.
- **Formatting (R-05):** unescaped Markdown inline-code delimiters in the three existing coordinator skill files; frontmatter, constitutional bounds and the one-Worker model retained.

## Required authority and evidence boundary

Ordinary analysis and code proposals from provided text remain possible under existing owner scope. Head owns first Worker selection. Before any real source write, live test, provider read, containment, merge, publication or deployment, use the actual connected host, user-approved action and current provider permissions. A GitHub comment, valid SHA, author-provided reference, `verification=PASS`, synthetic HostObservation or model-narrated audit is **not authenticated evidence**. Later specialists require an ordered Worker → Validate → logical Internal Auditor → Head cycle. Same-Worker repair requires Head review and remaining retry budget. Never assert a global cross-chat mutex.

## Logical Internal Auditor challenge

A producer can invent all required JSON fields, a logical PASS and a fake event chain. The development tests are therefore **structural and behavioral source checks only**: they cannot establish actual owner consent, authenticated role identity, fresh tool permissions, provider receipts, independent reviewer execution, or any genuine ChatGPT skill handoff. Report these gaps as `UNVERIFIED`, not acceptance.
