# 13 — Three connected decisions, scope and execution gates

**Status:** Architecture candidates documented, **not yet a working v0.0.2 release**. The user requested design resolution and documentation; this record does not imply owner has endorsed every engineering detail.

## Architecture decision summary
| ID | Concern | Selected future design | What it cannot guarantee yet |
| --- | --- | --- | --- |
| CTO-002-A | Single-lane | One Head/one active Worker in a single chat; optional managed relational lease + monotonic fencing + gateway + GitHub expected-SHA verification for enforced writes | Cross-session/global exclusion in skills-only mode; bypass-proof control over external writers |
| CTO-002-B | Authenticated evidence | Provider-backed evidence resolver, provenance ladder CLAIMED → OBSERVED → CORROBORATED → CRITERION_VERIFIED; dedicated Validate and distinct internal challenge | Cryptographic truth of every provider's records; unavailable logs; external approval |
| CTO-002-C | Specialist intelligence | Nine measured role-specific benchmark suites, trace-based tests, hidden holdouts, linked mission tests and no-regression promotion gate | Zero mistakes; actual measured gains before tests run; other-host equivalence |

## Relationship to 12 skills
No new runtime skill is required.
- **Mission Control:** scope, consent, budgets and required tool trust anchors.
- **OPS Director:** sole cross-team dispatch, retries, terminal decision and mission status.
- **Verification Gate:** evidence resolver + Validate + *distinct internal auditor phase*. Internal review must not impersonate an external independent approver.
- **Nine original Workers:** Yellow, Orange, Green, Blue, Red, Purple, White, Black, Gray Cell retain their canonical specialties. All produce the common completion envelope and skill-specific evidence/scorecard.

## v0.0.2 tier boundary
**Base (skills-first):** supports one-conversation guided/authorized missions where the host provides continuity; one Worker at a time by protocol, honest evidence verification where connected API tools exist; no mandatory database/gateway/paid platform, no global-lock guarantee, no owner runner. Read/advise and permitted scoped actions only within actually available permissions. Any mission requiring *guaranteed global exclusivity* blocks mutation without the enforced mode.

**Enforced cloud option (future implementation only):** when separately authorized and available, provider-managed SQL mission/lease store, controlled cloud mutation gateway, verified provider auth and evidence receipts. It is an optional safety mode—not a hidden always-on dependency. If actual tool permissions permit bypass writes, limit claim to **gateway-mediated exclusivity**.

Both modes use same mission/task/evidence semantics and make `GLOBAL_EXCLUSIVITY_UNVERIFIED` visible where applicable. Do not quietly widen product scope via a backend or use personal GitHub runners as production machinery.

## Implementation order and dependencies
1. **D0:** preserve existing idea branch and source decisions; no v0.0.1 edits.
2. **D1:** versioned mission/team/evidence/routing JSON schemas, state machine, trust distinctions and explicit capability modes; unit and negative tests.
3. **D2:** update nine specialist playbooks and evaluation fixtures without changing their roles; three coordination skills remain.
4. **D3:** integrate same-chat Head → Worker → Validate → Internal Auditor → Head and bounded repairs; verify exact source revision, authorization and no extra mandatory auditor thread.
5. **D4:** evidence resolver for authorized existing cloud connectors; test provider-to-criterion trust mapping; no fake PASS on missing tools.
6. **D5:** run role-specific benchmark pilot and integrated mission tests with frozen oracles; measure real quality and cost; no invented success.
7. **D6 (conditional):** build and pen-test optional managed cloud lease + write gateway **only if the owner authorizes infrastructure and its cost**; demonstrate expiry/fencing/duplicate/partial-failure behavior. Do not make this a dependency of base plugin use.
8. **D7:** exact-SHA source/package parity, actual ChatGPT host trials, security/contract regression, bounded internal audit and owner release authorization; no automatic merge/upload.

## Proposed future acceptance checklist
- [ ] No mandatory external auditor conversation, extra terminal or thirteenth skill.
- [ ] Head exclusively controls cross-team routing and terminal decision.
- [ ] Every team returns actual evidence, limitations and proper abstentions.
- [ ] Validate requires authenticated provider observations appropriate to each acceptance criterion.
- [ ] Internal Auditor rejects unsupported outcomes even after worker self-check.
- [ ] Source SHA change invalidates or re-establishes required proof; all required team work is validated at current revision.
- [ ] No unauthorized mutation through exposed host tools.
- [ ] In enforced cloud mode: prove conditional acquire, fencing, out-of-date writer denial, resource-level conflict isolation, gateway boundary and provider conflict handling.
- [ ] In skills-only mode: clearly mark cross-session exclusivity UNVERIFIED; block exclusive-write-required tasks when enforcement unavailable.
- [ ] Nine specialist scorecards and common mission tests actually executed with real trace/receipt references.
- [ ] Critical failures gate promotion independently of average scores; numeric floors registered before evaluating candidates.
- [ ] Cloud-only and no-runner prerequisite law unchanged.
- [ ] v0.0.1 release branch, main, installed plugin, Issue #4 branch and their CI untouched.

## Unresolved implementation choices requiring owner approval or real tests
- Which supported managed cloud service, tenancy/ownership model and spending cap, if any (no provider selected or provisioned).
- Whether v0.0.2 **ships only base mode** or also includes enforced cloud option; the option is not a promise to build infrastructure without approval.
- Production lease TTL, authorization grant expiry and recovery targets: must be tuned through failure testing, not guessed here.
- Which source- and provider-specific actions can be safely mediated/serialized.
- Exact quantitative skill thresholds by category/host, to be preregistered with sufficient dataset coverage.
- Actual host-integrated execution, identity, permissions and evidence capability checks.
